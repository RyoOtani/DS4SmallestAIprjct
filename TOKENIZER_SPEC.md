# TinyLLM Tokenizer Specification

> **Version**: 7.1 (2026-07-25) | **Format**: TOKBIN binary | **Vocab**: 32,000

## Overview

| Property | Value |
|----------|-------|
| Algorithm | ByteLevel BPE (GPT-2 architecture) |
| Normalization | NFKC (Unicode normalization) |
| Pre-tokenizer | ByteLevel with regex splitting |
| Vocabulary size | **32,000** |
| Special tokens | 21 (IDs 0–20, reserved) |
| Byte tokens | 256 (IDs 21–276) |
| BPE merge tokens | 31,723 (IDs 277–31,999) |
| Bundled format | `tokenizer.tokbin` (950 KB, binary) |
| Source format | `tokenizer/tokenizer.json` (HuggingFace compatible) |
| C runtime | `src/tokenizer.c` — loads `.tokbin` via `tl_tokenizer_load()` |

## Special Tokens (IDs 0–20)

**Single Source of Truth**: `include/tokenizer_ids.h`

## BPE Token ID Formula

```
Single-byte token:  ID = 21 + byte_value       (IDs 21–276)
BPE merge token:    ID = 21 + 256 + merge_rank  (IDs 277–31,999)
```

This formula is **identical** in Python (`tokenizers` library), C (`src/tokenizer.c`), and TOKBIN.

## File Formats

### 1. `tokenizer/tokenizer.json` (HuggingFace, Python)

Standard HuggingFace `tokenizers` library JSON format:
- `model.vocab`: display string → token ID mapping
- `model.merges`: list of `[token_a_str, token_b_str]` pairs in rank order
- `added_tokens`: special token definitions with fixed IDs

Used by: `AutoTokenizer.from_pretrained('tokenizer')`

### 2. `tokenizer.tokbin` (Binary, C Runtime)

Compact binary format loaded by C runtime. Generated by `export_tokenizer.py`.

```
Header (28 bytes):
  magic[4] = "TOKB" (0x424B4F54)
  version[4] = 2
  vocab_size[4] = 32000
  n_merges[4] = 31723
  n_specials[4] = 21
  max_token_bytes[4] = 114
  flags[4] = 0

Special IDs (84 bytes):
  21 × u32 special token IDs in canonical order

Vocab entries (variable):
  For each token ID 0..31999:
    byte_len[u16]
    raw_bytes[byte_len]  ← RAW bytes (NOT GPT-2 display encoding)
    padding to 4-byte boundary

Merge entries (380,676 bytes):
  For each merge:
    token_a[u32]  token_b[u32]  rank[u32]
```

Used by: `tl_tokenizer_load("tokenizer.tokbin")` in C.

### 3. `include/tokenizer_ids.h` (C Header)

Canonical C constants for all 21 special token IDs. Included by `include/tinyllm.h`.

## Loading

### Python (HuggingFace Transformers)

```python
from transformers import AutoTokenizer

# Load bundled 32K tokenizer (zero download)
tokenizer = AutoTokenizer.from_pretrained('tokenizer', use_fast=True)

# Verify
assert len(tokenizer) == 32000
assert tokenizer.bos_token == '<s>'
assert tokenizer.bos_token_id == 0
```

### C (tinyllm Runtime)

```c
#include "tinyllm.h"

// Load from .tokbin binary (generated by export_tokenizer.py)
tl_tokenizer_t *tok = tl_tokenizer_load("tokenizer.tokbin");

// Tokenize
tl_token_t tokens[256];
int n = tl_tokenize(tok, "Hello, world!", tokens, 256);

// Detokenize
char *text = tl_detokenize(tok, tokens, n);
printf("%s\n", text);  // "Hello, world!"

tl_tokenizer_free(tok);
```

### Building the Tokenizer

```bash
# Build tokenizer from scratch (requires tokenizers library)
python create_tokenizer.py                    # synthetic corpus (fast)
python create_tokenizer.py --vocab 65536      # larger vocab
python create_tokenizer.py --corpus-dir ./data  # real data (production)

# Export to C-compatible binary format
python export_tokenizer.py                    # tokenizer.json → tokenizer.tokbin

# Verify consistency
python test_3way_tokenizer.py                 # Python ↔ TOKBIN ↔ C
```

## FIM (Fill-in-the-Middle) Format

```
<fim_prefix>{prefix_code}<fim_suffix>{suffix_code}<fim_middle>
```

The model generates the missing middle section between `<fim_suffix>` and `<fim_middle>`.

## Tool Call Format

```
<tool_call>tool_name</tool_call>
<tool_response>result</tool_response>
```

Special tokens 12–15 are used for tool call boundaries.

## Consistency Guarantees

The following properties are **guaranteed** across Python and C implementations:

1. **Same special token IDs**: All 21 special tokens have identical IDs (verified by `test_3way_tokenizer.py`)
2. **Same encoding**: Identical input text produces identical token ID sequences (same BPE algorithm)
3. **BPE merge formula**: `ID = 21 + 256 + rank` is identical across implementations
4. **Round-trip**: `decode(encode(x))` preserves content (FIM/tool tokens intentionally stripped by `skip_special_tokens`)

Run verification: `python test_3way_tokenizer.py`
